# 0048. Find sources in code, and ask Claude Code on a Claude subscription only to judge them; start with ore candidates

- **Status:** Accepted
- **Date:** 2026-11-25
- **Revised:** 2026-11-25, rewritten in place at the owner's decision (the project is in development). As first accepted, the proposer was an agent that searched and fetched the web itself; its evaluation (below) used far too much of the plan, so code now finds and reads the sources, and the proposer only judges them.
- **Supersedes:** in part [0035](0035-propose-curated-facts-with-audited-agents.md): its models and interfaces, its spending caps and API rate limits, and where the audit log lives

## Context

[0035](0035-propose-curated-facts-with-audited-agents.md) decided that agents propose curated facts, code and a reviewer agent check them, and a person merges a pull request. It assumed the Claude API: each step a Dagster asset calling it with server-side web search and fetch, a spending cap per run, API rate limits, and the Message Batches API for large batches.

The project has no API budget. Its owner has a Claude Pro subscription, and wants agent runs to draw on that plan's usage, ideally hundreds of items without going past the five-hour limit. What we found on 2026-11-24 (Claude Code 2.1.330):

- **Claude Code can be scripted on a subscription login.** `claude -p` (print mode) runs one task and exits; it uses the Claude login unless an API key is set (`ANTHROPIC_API_KEY` takes precedence, and would bill the API). `--bare` skips the login, so it can't be used. `claude auth status` says which login is in use (`authMethod: claude.ai`, `subscriptionType: pro`).
- **It can return structured output** (`--json-schema`, the answer in `structured_output`), limit turns (`--max-turns`), offer only the tools named (`--tools`, `--allowedTools`), and run without CLAUDE.md, plugins, hooks or MCP servers (`--safe-mode`, `--strict-mcp-config`). With `--output-format stream-json --verbose` it prints every event: the tools used and their inputs, token usage, and an API-equivalent cost (`total_cost_usd`), which a subscription doesn't charge.
- **It reports the plan's usage.** Each call prints a `rate_limit_event` with the share used of the five-hour and weekly windows (`unifiedWindows.five_hour.utilization`, 0 to 1). Anthropic doesn't publish the limits themselves for Pro, only that they are shared between claude.ai and Claude Code.
- **Its web fetch returns a model's reading of a page, not the page.** A quote the agent copies through it can be a paraphrase.
- **An agent that researches on the web uses a lot of the plan.** The first evaluation (below), with an Opus proposer searching and fetching, used about 6–7 points of a Pro plan's five-hour window per item: most of it searches and fetches, 14 to 30 turns an item.
- **Anthropic's terms for the Agent SDK** say third-party products may not offer claude.ai login to their users. Scripting one's own Claude Code for one's own non-commercial project isn't addressed in what we read; the owner judges that.

## Decision

**Each agent step is one `claude -p` run** on the owner's Claude login, started by the pipeline as a subprocess. Every call:

- runs in an empty temporary directory with `--safe-mode`, `--strict-mcp-config` and `--no-session-persistence`, its own system prompt, a turn limit, and a JSON Schema for its answer;
- gets no tools: whatever a model needs to judge (the item, the passages, the page) is found and read by code and put in its prompt;
- takes its prompt on stdin, and prints stream-json, which the pipeline reads for the answer, the tools used, the usage and the plan's limits.

**A run refuses to start on anything but a Claude login.** If `ANTHROPIC_API_KEY` (or another credential that would take precedence) is set, or `claude auth status` reports anything but `claude.ai`, it stops before spending anything. It never turns on paid extra usage.

**Runs are sized by items and stopped by the plan's usage, not by dollars.** A run names how many items to work through, one at a time. Before each item it compares the usage last reported with two thresholds (by default 80% of the five-hour window and 90% of the weekly one) and stops if either is passed; if the limit is reached mid-item, it stops at once. A call that fails (out of turns, say) has used the plan all the same, so its usage counts too. Either way, the rest stay in the queue, and what was accepted so far still goes to a pull request. Concurrency is one: the owner's own use of Claude shares the same limits. The API-equivalent cost is recorded to compare prompts and models, not as a budget.

**The run is a Dagster job, `agent_curation`, launched by hand** with its size (`dg launch --job agent_curation --config-json …`). It is not an asset, so materializing everything never starts one.

**Code does everything that can be done the same way every time; a model only judges.** Finding the item, finding sources, reading them, choosing the candidate sentences, the quote, the citation and the URL are code. Which class the sentences support, and which sentence says so, is the model's. The same inputs give the same candidates, and the model step is one prompt with no tools, which a model run locally could answer the same way.

**The first task is ore candidates** ([0045](0045-bring-ore-minerals-in-from-upstream-roast-sulphides-and-queue-the-gaps.md)): for each mineral MRDS lists on many copper, iron and tin deposits, propose its ore crosswalk row.

1. **Find, in code.** The item: Wikidata's search for the mineral's name, keeping the item called exactly that (label or alias) that is a mineral: an instance of *mineral species* (Q12089225), or a subclass of a class of minerals, as Wikidata files limonite and native gold (a heuristic: a parent whose English label says "mineral"). A one-word name that finds only an element is tried again as "native <name>" (native silver, native gold). An item the ore crosswalk already has is skipped as decided; a curated thing's item (limonite) is left to a person, who decides how MRDS's name maps to it. Every item the search returned is recorded, with why it was or wasn't taken, whether or not one was. The sources: the pages the repository already cites (its crosswalk rows and the curated layer's references), then the open-access works OpenAlex finds for "<mineral> smelting" and "<mineral> ore" (five each), each downloaded once a run (HTML, PDF or plain text; on the public web only, redirects included; certificates checked against the operating system's trusted roots). The passages: the sentences that name the mineral and speak of ore, smelting, roasting or a metal, word for word, with the sentence before and after, never a figure's or table's caption; up to three a source and twelve in all, ranked across every source (smelting and the past first), the repository's own first on a tie. A mineral with no item, or no passages, is skipped without asking a model; it stays in the queue.
2. **Choose.** The proposer (Sonnet 5.5 at medium effort by default; each role's model and `--effort` are settings of the run), with no tools, gets the item, the classes and the numbered passages, and answers with a class or `none`, the number of the passage that supports it, what it supports and a short note, or `unsure`. Code makes the proposal: the quote is the chosen sentence, the citation and URL its source's (the repository's own citation, or one made from OpenAlex's record: authors as OpenAlex names them, year, title, venue), the id from MRDS's name, and the route it is mined like (the one the crosswalk's rows of that class use). A class no row uses yet (tin ore today) is left to a person.
3. **Check mechanically.** Code checks the class; the Wikidata item (it exists, wasn't merged, is called the mineral's name, and no crosswalk has it yet); the id is new; the source isn't one whose data may not be used (Mindat); and, on the page as downloaded, that it loads, that the quote is on it word for word (ignoring case and typography) and that the quote names the mineral. Most of these can't fail now that code chose the item and the quote; they stay, so nothing reaches the reviewer unchecked.
4. **Challenge.** The reviewer (Sonnet 5.5 at high effort by default: the last check before a person thinks harder than the proposer) gets the proposal, the Wikidata item and the text around the quote, all as the pipeline downloaded them, and none of the proposer's reasoning or the other passages it was offered. It answers accept, revise or reject, with objections tied to parts of the proposal.
5. A failed check or a "revise" goes back to the proposer with the reasons, to choose again among the same passages. Each item gets two proposals at most.
6. **Gate.** Accepted rows are written into the crosswalk in a temporary git worktree on a new branch, `agents/<run>`, from `origin/main`. There Wikidata's labels and quantities for the new items, and OpenAlex and Crossref for the new citations ([0047](0047-check-citations-against-openalex-and-crossref.md)), are downloaded as they would be by hand, and the graph is built with all its tests. The citation check's result is noted on each row, and only a DOI that leads to another work (`doi_disagrees`) drops one, after which the rest are checked again: the row's own page was downloaded and its quote found, and many books, reports and web pages are in neither index, which [0047](0047-check-citations-against-openalex-and-crossref.md) says doesn't make a work doubtful. A row rejecting a mineral (class `none`) builds nothing, so its reference isn't looked up; its page and quote were checked all the same.
7. **Pull request.** What passes is committed with the refreshed cold backups, the regenerated works cited and the run's summary, pushed, and opened as a **draft** pull request with the owner's `gh` login, titled "Agent proposals: …" (its commit is a conventional one). Text from pages and agents in the pull request is written so that it can't mention anyone on GitHub. The run never merges.

**The crosswalk gains two columns**: `quote`, the passage word for word, and `proposed_by`, the run. An agent's row leaves `status` empty, so its reference is `unverified` ([0008](0008-record-the-basis-of-every-number.md)); passing the agents' review isn't reading the work. The build carries the quote into the mineral's reference (the reference schema gains an optional `quote`), and `proposed_by` into the provenance of the mineral, its deposit and its route. The app's detail pane shows the quote under the reference, and "Proposed by an agent, run …" beside where the node came from.

**A run records what code read**: the item found (or why none was), how many passages from how many sources, and in its summary the OpenAlex searches made and pages downloaded, since searches count against OpenAlex's daily allowance ([0047](0047-check-citations-against-openalex-and-crossref.md)).

**The audit log is an append-only DuckDB file, `audit/agents.duckdb`, kept out of git.** Its tables (`run_starts`, `calls`, `checks`, `outcomes`, `run_ends`) only ever gain rows: every call with its prompt, prompt version (the prompt file's hash), model (the alias asked for, such as `opus`, and the model it ran on, which the alias stops meaning when a newer one comes out) and settings, the answer, every tool call, the usage, the plan's limits and the events printed; every check; every outcome (a later outcome of an item supersedes an earlier one). The login is recorded only as its method and plan, never the account. A run's end and its summary are recorded however it ends, an error included. Each run's summary is written beside it (`audit/runs/<run>.json`) and, for a run that opens a pull request, committed with it (`data/agent_runs/<run>.json`), so what was merged is explained even if the audit file is lost.

**An evaluation run asks the agents again about the minerals a person already decided** (the ten rows reviewed by hand, kept in `pipeline/src/capabilities_pipeline/agents/evaluation/ore_candidates.csv`), treating those rows as undecided. It goes through every step, the gate included, opens no pull request, and scores the answers against the person's: how many were right, how many were accepted, and above all how many accepted were wrong. The first run is an evaluation, to measure both the quality and how much of the plan an item uses before running real queue items.

## Consequences

- Runs cost no money and need no API key, but they share the owner's plan with their own use of Claude. How many items fit in five hours isn't published anywhere; the evaluation measures it, and each run records the plan's usage before and after.
- Usage, not dollars, now bounds a run. The thresholds stop a run before the owner is locked out of Claude for the rest of the window.
- One item at a time is slow. Nothing urgent depends on it.
- A mineral is only as well covered as the repository's sources and OpenAlex's open-access works: one neither speaks of is skipped. Agents can't go looking further; a person can, or a later fallback can (with a tight turn budget).
- Each item makes two OpenAlex searches, on top of the gate's downloads, and the free daily allowance is small: three find-only runs and one gate on 2026-11-25 spent it. A run stops when OpenAlex refuses a search (429), rather than skip items as if nothing spoke of them; a free API key (`OPENALEX_API_KEY`) raises the allowance.
- A run can find without judging (`find_only`): it records what each item would be offered and asks no model, for none of the plan. Tuning what code finds is done that way.
- A quote can't be a paraphrase, and a citation can't be invented: both come from code.
- An evaluation leaves out pages only the person's rows cite, but pages the curated layer also cites stay in the library (the Taldysai paper, for the copper rows), so those minerals are easier there than a new one would be.
- The gate downloads the reference candidates in full (about a minute and a half, and about $0.03 of OpenAlex's free $0.10 a day), so a few runs a day stay within the free allowance.
- The pull request carries refreshed cold backups of three datasets, as any change to the crosswalk would.
- The report button, withdrawal, and batch re-checks by run ([0035](0035-propose-curated-facts-with-audited-agents.md)) are still to come, as are sources for routes with only unverified references.
- Whether this use of a subscription is within Anthropic's terms is the owner's call; if it isn't, the same pipeline can call the API by swapping how a step is asked.

## Evaluation

**2026-11-25, Opus 5.5 proposing and reviewing, default effort, the ten rows a person reviewed** (run `ore-20261125-162547`, 30 minutes): 9 proposed, 9 right (class and Wikidata item), 6 accepted, **none accepted wrong**. Chalcocite was sent back twice (the reviewer caught a citation title that didn't match the page); Azurite's page failed Python's certificate check though browsers open it; Tenorite's proposer ran out of 30 turns; Siderite was dropped at the gate only because its web page isn't in OpenAlex or Crossref. Each led to a fix: a failed call's usage is counted, certificates are checked against the system's roots, and only a wrong DOI drops a row at the gate.

**The quality held, but the usage didn't.** The run took the plan's five-hour window from 6% to 73%, about 6–7 points an item, and the weekly from 30% to 34%; 21 calls, 39 searches and 92 page fetches, about $6 at API prices. On Pro that is about 12 items a five-hour window and roughly 140 a week, not the hundreds hoped for. **Run that way, the plan is judged a failure.** (A 2-item smoke run earlier had suggested about 1.5 points an item; it was wrong.)

What follows, in order:

1. Code finds and reads the sources, and the proposer only judges (this revision), on Sonnet 5.5 at medium effort; then one more evaluation. Haiku isn't tried: a model that small would be better run locally.
2. If that doesn't bring an item's use of the plan to a reasonable level, Claude is dropped for this work, and the model steps wait for a model run locally on the owner's own machine (from the week of 2026-11-30). The finding, checks, gate, audit log and pull requests don't depend on which model answers; only how a step is asked would change.

**2026-11-25, the scripted design: Sonnet 5.5 at medium effort choosing, Opus 5.5 reviewing** (run `ore-20261125-213323`, 8 minutes): 8 proposed, 8 right, 6 accepted, **none accepted wrong**; Pyrite and Magnetite honestly `unsure`. The five-hour window went from 8% to 13%, about **0.5 points an item** against 6–7 before, and the weekly by under a point; 26 calls, $0.89 at API prices against $6.09, two-thirds of it the Opus reviewer. On Pro that is in the order of 140 items a five-hour window. **The scripted design is viable on the subscription.** Its weak spots led to three fixes: a figure caption accepted as Bornite's quote (captions are no longer offered, and the reviewer sends back a quote that doesn't carry the claim by itself); Cuprite sent back over author names garbled by turning them into "Surname, I." (OpenAlex's names are kept as given, and the reviewer doesn't object to a citation's style, which the proposer can't change); and Magnetite's best passage crowded out by weaker ones read first (passages are ranked across sources).

**2026-11-25, with those fixes, Sonnet 5.5 at high effort reviewing** (run `ore-20261125-215613`, 7 minutes): 9 proposed, 9 right, 8 accepted, **none accepted wrong**; Magnetite and Cuprite now accepted, Bornite sent back twice for a quote that was "a hedged side remark", Pyrite `unsure`. The five-hour window went from 19% to 23%, about 0.4 points an item; $0.48 at API prices, the reviewer $0.26 of it against Opus's $0.61. It caught what Opus caught for under half the cost, so it is the default. Neither reviewer noticed two quotes cut off mid-sentence ("… CuFeS2 (Fig." and "… Tylecote et al."): the sentence splitter broke at abbreviations, and now mends such splits.

## Alternatives considered

- **The Claude API, as 0035 planned.** Server-side tools, batches and exact pages from its fetch tool, but it bills per token, and there is no budget for it.
- **The Claude Agent SDK.** It drives the same agent loop from Python, but its documentation asks for an API key and says third-party products may not use claude.ai login. The CLI is the documented way to use a subscription without a key.
- **Let the proposer research on the web itself**, as first built. It finds sources code can't, but it used 6–7 points of the five-hour window an item (see *Evaluation*), and its choices of what to read were not repeatable.
- **A web-searching proposer as a fallback** for minerals code finds nothing for. Left out until an evaluation shows how many that is.
- **Let the agent's fetch tool be trusted for quotes.** Simpler, but it would let a paraphrase or an invented sentence through, which is exactly what 0035's mechanical checks are for.
- **Run items in parallel.** Faster, but it would burn through the shared limits in bursts and make the thresholds coarse.
- **A spending cap from `--max-budget-usd`.** It caps the API-equivalent cost, which a subscription doesn't charge; the plan's usage, which it does count, is what a run must stay under.
- **Let the agent choose the route a mineral is mined like.** It is mechanical, given the class, so code does it.
- **Keep the audit log in the warehouse** (`build/warehouse.duckdb`), as 0035 suggested. Everything in `build/` is generated and may be deleted at any time; the audit log must outlive every build.
